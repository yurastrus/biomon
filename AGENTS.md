# Контекст проекту для Codex

## Проект
Flask-додаток biomon. Містить модуль фотопасток (camera traps), модуль PAM, та інші.

## Структура репозиторію
- `app/camera_traps/` — сабмодуль `yurastrus/shared-ct` (branch: main)
- `app/pam/` — сабмодуль `yurastrus/shared-pam`
- `app/docs/` — модуль інструкцій/вікі (майбутній сабмодуль `yurastrus/shared-docs`): сторінки в головній БД, права редагування по темах (`doc_editor`), захист сторінок (`locked`), історія (`doc_revision`), картинки в `instance/docs_uploads` (включити в бекап). Див. `app/docs/README.md`. **Будь-яке завдання «зробити/перекласти/оновити інструкцію на сайті» → спершу прочитати `app/docs/AGENTS.md`** (двомовність, бандл uk.md/en.md, імпорт лише на сервері, чернетка за замовчуванням)
- `tests/` — unittest тести (наразі тільки `test_data_export.py`)

**Важливо:** `app/camera_traps` використовується також у `/var/www/myproject` на сервері. Зміни в сабмодулі треба комітити окремо в `shared-ct`, потім оновлювати посилання в обох проектах.

## Відомий баг: idle in transaction (частково виправлено 2026-04-06)

### Що виправлено
`app/camera_traps/data_export.py` — замінено `get_ct_session()` + `session.connection()` на `engine.connect()` як context manager. Тепер з'єднання гарантовано закривається.

### Що залишилось
`app/camera_traps/routes.py` — dashboard та інші маршрути використовують `ct_session` (scoped_session). `get_ct_profile()` у `app/models/__init__.py` сама викликає `close_ct_session()` у своєму `finally`, що порушує lifecycle сесії. Через це після кожного запиту до dashboard може залишатись `idle in transaction` по одному на воркер.

**Страховка:** `idle_in_transaction_session_timeout = 5min` встановлено в `postgresql.conf` — PostgreSQL сам прибиває зависші транзакції.

### Правильний подальший фікс
Прибрати `finally: close_ct_session()` з `get_ct_profile()` — сесією має керувати виключно маршрут. Потребує обережного тестування.

### Що НЕ робити
Не додавати `_ct_session_factory().rollback()` перед `remove()` у `close_ct_session()` — це expire всі ORM атрибути, і потім `ct_profile.camera_trap_role` у шаблоні кидає `DetachedInstanceError`. Вже спробували — зламало сайт.

## Швидке завантаження (upload-fast, Beta — з 2026-05-24)

Паралельний шлях для великих наборів фото (10k–100k+). Існує разом зі
старим `/upload` — нічого з нього не видалено.

### Що нового
- **Route:** `GET /<lang>/camera-traps/upload-fast` (manager+).
- **Шаблон:** `app/camera_traps/templates/upload_fast.html` — клон upload.html
  з паралельним JS (пул із 4 одночасних `process-single`) і polling-фіналізацією.
- **Модуль:** `app/camera_traps/fast_upload.py` — окремо від `utils.py`.
- **SQL-групування:** `group_batch_into_series_sql(batch_id)` — один CTE-запит
  через window-функції (`LAG`, `SUM`, `ROW_NUMBER`). Single-pass над усім batchʼем,
  ідемпотентний, чистить partial Observations попередньої спроби.
- **Async:** `start_async_grouping(batch_id)` — `threading.Thread`. Точка
  заміни на Celery надалі — підмінити тіло на `task.delay(batch_id)`.
- **Recovery:** `recover_stale_grouping_batches()` для виклику з app factory
  при старті — переводить «застряглі» батчі (`status='grouping'` старші 30 хв)
  у `'failed'` для retry. Поки не зачеплено старт app — підключити при
  переході з threading на Celery.
- **Нові ендпоінти:**
  - `POST /api/finalize-batch-async` → 202, стартує фонове групування
  - `GET /api/batch/<id>/uploaded-files` → список залитих файлів (для resumable)
  - старий `/api/batch-status/<id>` переюзаний для polling
- **Нові стани `UploadBatch.status`:** `ready_to_group`, `grouping` (додатково
  до існуючих `uploading` / `completed` / `failed`). Колонка — звичайний
  VARCHAR(20) без CHECK, тож міграція не потрібна.

### Інваріант
Групування викликається лише ПІСЛЯ того, як усі фото batchʼа зафіксовані в БД
зі `status='uploaded'`. Це гарантує single-pass над повним набором — серії
не розриваються на межах чанків. Реалізовано в SQL: один CTE-запит читає всі
photos одного batchʼа разом.

### Деплой
1. У сабмодулі `shared-ct` уже задеклароване `Index('idx_photos_batch_captured', ...)`.
2. Створити індекс на проді одноразово (`create_all` не додає індекси
   на існуючі таблиці):
   ```bash
   venv/bin/python -m scripts.init_fast_upload      # Linux/прод
   venv/Scripts/python -m scripts.init_fast_upload  # Windows/dev
   ```
   Скрипт ідемпотентний (`CREATE INDEX IF NOT EXISTS`).
3. Гарантувати gunicorn `--timeout` ≥ 120 для biomon — default 30 замалий
   для одного `process-single` зі стисненням мініатюри (фронт чекає до 60с).
4. **Коміти у сабмодулі окремо**: зміни `models.py` йдуть у `shared-ct`,
   далі оновити посилання у `biomon` і `/var/www/myproject`.

### Куди рухатись далі (після валідації Beta)
- Перевести `start_async_grouping` на Celery + Redis (точкова заміна).
- Викликати `recover_stale_grouping_batches()` з app factory.
- Прибрати посилання на старий `/upload` зі стартової сторінки. Код старого
  шляху залишається.
- UNIQUE-індекси на `(upload_batch_id, original_filename, captured_at)` —
  тоді в `process_single_photo` можна прибрати preflight JOIN-перевірки на
  користь ловлі IntegrityError.

## Переклади (i18n) — ОБОВ'ЯЗКОВИЙ цикл при будь-якій зміні `_()`/`_l()`

Якщо додаєш/змінюєш рядки в `_(...)`, `_l(...)`, `lazy_gettext(...)` (у .py чи в
шаблонах, включно з JS у шаблонах) — **завжди** прогнати ці 4 кроки повністю:

```bash
# 1. Витяг усіх _(), _l(), lazy_gettext() в .pot  (флаги -k ОБОВ'ЯЗКОВІ)
venv/Scripts/pybabel extract -F babel.cfg -k _l -k lazy_gettext -o messages.pot .

# 2. Merge у наявні .po (нові рядки додаються, старі лишаються)
venv/Scripts/pybabel update -i messages.pot -d translations

# 3. Перекласти нові msgstr ВРУЧНУ в translations/en/LC_MESSAGES/messages.po
#    + ЗНЯТИ рядок `#, fuzzy` з кожного виправленого запису.
#    uk-файл НЕ чіпаємо (msgid вже українською → fallback коректний).

# 4. Скомпілювати .po → .mo  (флаг -f ОБОВ'ЯЗКОВИЙ!)
venv/Scripts/pybabel compile -f -d translations
```

**Чому саме так (не пропускати флаги):**
- `update` НЕ приймає `-k` (тільки `extract` приймає).
- `compile` ЗАВЖДИ з `-f` (`--use-fuzzy`): без нього fuzzy-записи випадають із
  `.mo` і результат розходиться зі стандартним білдом.
- Каталоги: `translations/` у КОРЕНІ проекту (НЕ `app/translations`).

## Автопризначення біотопів з лендковеру (Beta — з 2026-07-15)

Кнопка в адмінпанелі CT (`/admin`, admin-only), що фоново призначає біотопи
локаціям за ESA WorldCover (10 м) через Google Earth Engine. Заповнює прогалину:
894 з 926 локацій не мали біотопів → ламались біотопні фільтри дашбордів.

### Як працює
Для кожної локації береться гістограма класів покриву в радіусі навколо точки
(`ee.Reducer.frequencyHistogram` над `Point.buffer(radius)`), топ-N класів
переводяться в біотопи через таблицю `biotope_landcover_map` і **додаються** до
локації (наявні НЕ стираються — `ON CONFLICT DO NOTHING` на `location_biotopes`).
Радіус (дефолт 100 м) і top_n (дефолт 3) — параметри форми. Unmapped-класи
(забудова, рілля) ігноруються, тож top_n рахує біотопи, не класи → стійкість до шуму.

### Ключові файли (сабмодуль shared-ct)
- `app/camera_traps/biotope_autoassign.py` — самодостатній модуль (НЕ імпортує
  `app.sdm` заради портативності): `gee_landcover_available()` (дешевий gating),
  свій `_initialize_gee()` (ледачий `import ee`, ключ з `GEE_SERVICE_ACCOUNT_KEY`),
  `get_landcover_histograms`, `select_biotopes_from_histogram` (чиста логіка,
  тестована), `assign_biotopes`, `start_async_assign` (threading — точка заміни
  на Celery), статус у `calculation_log` (`source_name='biotope_autoassign'`).
- `models.py` — `BiotopeLandcoverMap(worldcover_class UNIQUE, biotope_id FK)`.
- `routes.py` — `POST /admin/biotopes/auto-assign` (202/409/**503** якщо GEE нема),
  `GET .../status` (polling).
- `templates/admin.html` — секція «Біотопи з лендковеру»: кнопка + поля радіус/top_n
  + polling. Кнопка ховається/вимикається, якщо `gee_available` false. Відповідність
  клас→біотоп в UI НЕ редагується — тільки в БД (`biotope_landcover_map`).

### Graceful degradation (модуль публічний)
Нема пакета `ee` АБО ключа GEE → `gee_landcover_available()` false → секція
рендериться вимкненою, роут повертає 503. Помилка в прогоні → `try/except` пише
`failed` у статус. Сайт не падає в жодному разі.

### Деплой
1. Створити таблицю + засіяти дефолти (ідемпотентно):
   ```bash
   venv/Scripts/python -m scripts.init_biotope_autoassign   # dev (тунель 5433)
   venv/bin/python -m scripts.init_biotope_autoassign        # прод
   ```
   Скрипт також створює **загальні біотопи** під класи WorldCover (ідемпотентно
   по `name_ua`): Ліс, Чагарники, Рілля, Забудова, Оголений ґрунт, Водойми,
   Водно-болотне угіддя. Дефолтний мапінг → на ці загальні (10→Ліс, 20→Чагарники,
   30→Лука, 40→Рілля, 50→Забудова, 60→Оголений ґрунт, 80→Водойми, 90→Водно-болотне).
   WorldCover надто грубий, щоб відрізнити хвойний/листяний ліс чи ставок від озера,
   тож специфічні біотопи (підтипи лісу, Стави, Торфовище, Берег річки) лишаються
   для ручного тегування. Класи 70/95/100 (сніг, мангри, мохи) — нерелевантні для України.
2. Коміти в сабмодулі окремо → оновити посилання в `biomon` і `myproject`.
3. Масовий прогін запускається кнопкою адміном (не автоматично).

## Зсув часу батчу на /upload-fast (з 2026-10-05)

Опційний крок 3 на `/upload-fast` виправляє годинник камери для всього батчу
(літній час, AM/PM, не та дата, скидання на 2000 рік). Старий `/upload` не чіпано,
уже завантажені батчі не виправляються.

- **Зсув тримає сервер:** `upload_batches.time_offset_seconds` (INTEGER, NOT NULL,
  default 0) задається в `create-batch` і додається в `process_single_photo`
  (їде в тому ж `UPDATE … RETURNING processed_files`). Оригінал відновлюється як
  `captured_at - offset`.
- **Зсув додається ДО перевірки правдоподібності** (`extract_datetime_from_exif(offset=)`):
  так скидання на 2000 рік виправляється, а в майбутнє зсунути не вийде.
- **Не зсуваються:** заглушка 1900 (фото без EXIF) і кадри з відео.
- Межа ±50 років (`MAX_TIME_OFFSET_SECONDS` = `MAX_OFFSET_SECONDS` у
  `static/js/time_shift.js`, паритет перевіряє тест). Лише дні/год/хв/с.
- Браузер (`time_shift.js` + exifr з jsdelivr) лише показує превʼю й рахує зсув.
  exifr: НЕ використовувати `pick` (падає в lite-збірці) і `reviveValues`
  (зсуває на часовий пояс браузера).
- Перевірка на локальній папці без БД: `venv/Scripts/python -m scripts.preview_time_shift "<папка>" -3600`.

**Деплой:** спершу `venv/bin/python -m scripts.init_time_offset` (ідемпотентно),
ПОТІМ код: модель оголошує колонку, тож без неї падають запити до UploadBatch.
Далі сабмодуль `shared-ct` → посилання в `biomon` і `/var/www/myproject`.

## Аналіз прогалин у даних CT (Beta, з 2026-10-14)

Сторінка `GET /<lang>/camera-traps/analysis/gap-analysis`: де відсутність
реєстрації виду щось означає. Три виміри окремо: зусилля (камеро-доби),
повнота виявлення видів, покриття сезонів; плюс «чи міг вид бути пропущений».

- `gap_metrics.py` — чиста математика (Chao2, sample coverage, крива накопичення,
  чутливість до пулу, ядро зусиль, EEA-сітка EPSG:3035 з кодами як у SDM).
- `gap_analysis.py` — читання ct_db в `GapData` і побудова шарів.
- `gap_routes.py` — сторінка + `/api/gap-analysis/{grid,cell/<code>,kernel,biotopes}`.
  Окремо від `routes.py`; кеш 10 хв на процес, ключ містить права доступу.
- Перевірка на справжній БД (лише читання): `venv/Scripts/python -m scripts.probe_gap_analysis`.
- **Доступ:** сторінка, картка й API для всіх залогінених (`GAP_ANALYSIS_MIN_ROLE = None`
  у `gap_routes.py`). Дані: публічні локації + установи користувача
  (`get_institution_filter`), адмін бачить усе. Обмежити знову: вписати роль у константу.
- `role_required` для анонімного падає (`auth.login` не існує) — завжди ставити
  `login_required` перед ним.

**Що варто знати:**
- Камеро-доба = правило календаря покриття (розгортання ∪ дні з серіями, прогалини
  ≤ `COVERAGE_MAX_GAP_DAYS`) **мінус** дні лише з неверифікованими серіями;
  розгортання без жодної верифікованої серії не рахується.
- Sample coverage на реальних даних майже скрізь 1.0 (домінують козуля, олень,
  кабан), тому зведений індекс бере **чутливість до пулу** (рідкісні види важать
  стільки ж, скільки звичайні). Пул локальний: види в радіусі 50 км.
- Імовірність виявлення наївна (частка одиниць із реєстрацією там, де вид є),
  оцінка зверху. Не підміняє модель зайнятості.
- **Одиниця за замовчуванням: камеро-тиждень** (`DEFAULT_UNIT`). Реєстрації в сусідні
  дні автокорельовані (0,235 проти середньої p 0,080), добові одиниці надто оптимістичні.
  Для виявлення p рахується на повний тиждень-еквівалент (камеро-доби / 7), інакше
  розкидані дні стають «повними тижнями».
- **Неверифіковане не зникає:** дні лише з pending-серіями (47 % на 10.2026) не є
  зусиллям, але зберігаються як `pending_days`; клітинки без жодного перевіреного дня
  мають статус `unverified` (фіолетові), шар «Верифіковано».
- `unstable` = Q1>0, Q2=0: bias-corrected f0 тоді Q1(Q1−1)/2, а з одним синглтоном 0
  (coverage 1.0, як і в iNEXT). Значення лишається, але позначене.
- Аудит припущень на реальній БД: `venv/Scripts/python -m scripts.audit_gap_analysis`.
- Деплой: нових таблиць і пакетів нема (pyproj, shapely вже є). Сабмодуль
  `shared-ct` → посилання в `biomon` і `myproject`.

### GBIF на сторінці прогалин CT (з 2026-10-16)
- `gbif_cache.py` (shared-ct): пошуковий API GBIF → фільтри → агрегація в 1 км
  EEA → таблиці `gbif_taxa`, `gbif_cell_counts` (створює `scripts.init_gbif_cache`).
  Оновлення фоном кнопкою адміна на сторінці (~2 хв), статус у `calculation_log`
  (`gbif_cache`). Кеш відсутній → сторінка просто каже «не завантажено».
- Види: ссавці, яких може зафіксувати камера (ряди/родини в `CAMERA_DETECTABLE_TAXA`)
  + усі види з камер. Домашні форми й тюлені виключені.
- **Власний датасет Розточчя в GBIF (b587c2e3) виключено** — це 30 % записів району.
- Вікно років: `gbif_year_window()` (зараз 20 років), кеш тримає 40.
- Точність: запис іде в клітинку, лише якщо похибка ≤ розміру клітинки;

## Кілька видів в одній серії CT (задеплоєно 2026-10-30)

- Верифікатор може назвати кілька видів: рядок на (фото, людина, вид), у кожного
  своя кількість і теги. Ключ `UNIQUE NULLS NOT DISTINCT (photo_id, user_id, species_id)`
  (`scripts.init_multi_species`, сухий прогін за замовчуванням, `--apply` ДО коду).
- **Єдине правило консенсусу: `app/camera_traps/consensus.py`.** Прийняті види серії =
  колишній переможець (завжди) + кожен вид, який назвали БІЛЬШЕ половини верифікаторів.
  Голоси рахуються людьми, не рядками. Новий читач даних CT бере `consensus_ctes()` і
  фільтр `rc.accepted`, а не власний `ROW_NUMBER ... rn = 1`.
- Серії рахувати `COUNT(DISTINCT observation_id)`: серія з двома видами дає два рядки.
- Закриття серії (`consensus.can_close`): якщо всі назвали по одному виду, діє старе правило.
  Якщо хтось назвав кілька, кожен названий вид має бути вирішений: більше половини
  прийнято, менше відхилено, рівно половина = серія чекає наступного верифікатора.
- Серія з прапорцем 🚩 не чиститься (нічний `cleanup_old_photos`, кнопка видалення
  оригіналів), доки адмін не зніме прапорець. Знімати прапорець може лише адмін.
- «Інший вид» (-2) захищає серію від очищення, лише якщо він серед ПРИЙНЯТИХ видів
  (`background_tasks._kept_by_consensus_ids`), а не будь-який один голос.
- «Неможливо визначити» (-6) як головний вид закриває серію лише від 5 верифікаторів
  (`consensus.UNIDENTIFIABLE_MIN_VOTERS`). Старі закриті з <5 голосами очищення не чіпає;
  повернути їх у чергу: `scripts.reopen_unidentifiable` (сухий прогін, `--apply`).
- Нічия без ключа виду вирішується `species_id DESC` (раніше довільно, ~500 серій).
- `analytics_calculator` (місячна активність, тренди) рахує будь-який названий вид без
  консенсусу, так було й до зміни.
- Перевірка без ризику для проду (пісочницю після деплою видалено, як відтворити: WORKLOG 2026-10-29): кластер на сервері (порт 5544,
  `/mnt/HC_Volume_104588395/ms_sandbox`), тунель `ssh -N -L 5545:localhost:5544 yurastrus.dev`,
  `scripts/sandbox_server.py` (порт 5001), `scripts.snapshot_ct_stats` (знімок і diff статистик).
  **Локальний `.env` CT_DATABASE_URL = ПРОД.**

## CSV-бекап даних фотопасток (другий рівень, з 02.09.2026)

Нічний `full_backup.sh` дампить бази й GeoServer. Дамп рятує тільки того, хто
може розгорнути його назад у biomon. Другий рівень пише **ту саму таблицю, що
й сторінка експорту**, у CSV — окремим файлом на кожну установу.

### Де що лежить
- `app/backup/storage.py` — бекенди сховищ (`LocalStorage`, `RcloneStorage`)
  за спільним інтерфейсом `put / read_manifest / write_manifest / rotate`.
  Nextcloud надалі = ще один клас тут плюс рядок у конфізі, код експортера не
  чіпається.
- `app/backup/ct_csv.py` — сам експортер. Рядки бере з
  `app.camera_traps.data_export.get_ct_occurrence_data` (та сама функція, що
  за `/api/data-download`), тож колонки не можуть розійтися з UI.
- `config.py` → `CT_CSV_BACKUP` — корінь, кількість версій, список сховищ.
- `deploy/ct_csv_backup.sh` — обгортка для cron / `full_backup.sh`.
- CLI: `flask ct-csv-backup [--dry-run] [--keep N] [--institution RSNR]`.

### Розкладка на диску
```
/home/yura/backups/            (симлінк → /mnt/HC_Volume_104588395/backups)
├── postgres/                  ← full_backup.sh
├── geoserver/                 ← full_backup.sh
└── phototraps_data/           ← цей модуль
    └── Roztochya_Nature_Reserve/
        ├── RSNR_ct_occurrence_2026-09-02.csv
        ├── RSNR_ct_occurrence_2026-09-01.csv
        └── manifest.json
```
Назва папки — `Institution.name_en`, зведена до ASCII (`slugify_folder`);
без англійської назви — `institution_<id>`. Префікс файлу — `Institution.code`.
Обидва беруться з БД, у коді не захардкоджені.

### Google Drive безкоштовно
`phototraps_data/` лежить усередині `$BACKUP_ROOT`, який `full_backup.sh` уже
дзеркалить через `rclone sync … gdrive_backup:backups/my_server`. Тому окремого
завантаження нема. Бекенд `rclone` вмикається лише тоді, коли ціль **інша** —
задати `CT_CSV_BACKUP_REMOTE` (напр. `nextcloud:biomon/ct`).

### Перевірка змін
Експортер хешує згенерований CSV (sha256) і порівнює з `manifest.json` у
призначенні. Байти ті самі — файл не пишеться взагалі. Тихий парк коштує один
запит на ніч і нуль запису на диск, що важливо на томі, зайнятому на 96%.
Маніфест окремий у кожного бекенда: віддалене сховище, яке лежало вчора,
дожене само, навіть якщо локальна копія вже свіжа.

### Ротація — рахунок, не вік
`KEEP_VERSIONS` (дефолт 2) тримає N найновіших файлів на установу.
`full_backup.sh` чистить дампи через `find -mtime +$RETENTION_DAYS`, і
`RETENTION_DAYS=0` там означає «старше за добу — видалити». Для CSV це
не годиться: файл переписується тільки коли дані змінилися, тож парк без
активності втратив би через добу свою єдину копію. Тому змінна своя,
і вона рахує версії. `keep=0` затиснуто до 1 — «бекап без жодного файлу»
не є станом, у який модуль дозволяє собі впасти.

### Фільтри бекапу (не дефолти сторінки)
`export_mode='human_ai'`, `filter_type='all'`, `aggregation='none'`,
період `1900-01-01 … сьогодні`. Тобто консенсус + усі конкурентні визначення
неузгоджених серій + серії з самим лише AI-прогнозом, разом із порожніми
кадрами, людьми й авто. Сторінка експорту за замовчуванням дає значно вужчу
вибірку (консенсус, тільки тварини, поточний рік) — це доречно людині й
недоречно бекапу.

### Ізоляція збоїв
Збій одного бекенда → попередження, решта пишуть. Збій однієї установи →
її помилка в звіті, решта установ бекапляться. Команда завершується кодом 1,
якщо впала хоч одна установа, але вже записані файли лишаються на місці.

### Деплой (потребує sudo, робиться вручну)
1. `install -m 755 /var/www/biomon/deploy/ct_csv_backup.sh /usr/local/bin/`
2. Вставити блок `4b` у `/usr/local/bin/full_backup.sh` **перед** секцією 5
   (rclone sync) — текст блоку в шапці `deploy/ct_csv_backup.sh`.
3. Перевірити вручну: `/usr/local/bin/ct_csv_backup.sh --dry-run`

## Відео з фотопасток (Beta — з 2026-09-18)

Окрема сторінка `GET /<lang>/camera-traps/upload-video`. **Менеджери й адміни** (з 2026-11-03,
до того лише адмін): час тепер береться з метаданих або вписується вручну біля першого кадру,
тож хибний час видно до запису. Кадри йдуть лише на керовані локації (`_batch_access_error`
у process-frame). Картка на хабі під `can_upload or is_admin`. Тести — `tests/test_ct_video_access.py`. Стару
`/upload-fast` не чіпано. Кліп ріжеться на кадри по одному на секунду, тобто
10-секундне відео стає серією з 10 фото, а 70 МБ — приблизно 3 МБ.

### Нарізка — у браузері, не на сервері
`app/camera_traps/static/js/video_slice.js`. Два шляхи:
- **AVI + MJPG** — без декодування взагалі: у RIFF кожен чанк `00dc` уже цілий
  JPEG із власними DQT і DHT. Виміряно: 74 МБ → 10 кадрів (2.6 МБ) за 25 мс.
- **H.264 у MP4/MOV** — `<video>` + перемотка + canvas. Близько секунди на кадр.

Формат, який браузер не відкриває, отримує чесне «не підтримується». Серверної
нарізки нема свідомо: відео на сервер не потрапляє взагалі, тож ні ffmpeg, ні
тимчасового сховища, ні прибиральника не потрібно.

### Час зйомки визначає сервер
`app/camera_traps/video_timestamp.py` (розпізнавання) і `video_upload.py`
(межа з браузером). Залежності — лише Pillow і numpy, обидві вже є.

Клієнту час **не довіряють**: сервер читає кадри й повертає час старту кліпу в
підписаному токені (`itsdangerous`), який браузер має повернути незміненим із
кожним кадром. У підписі — `batch_id` і ім'я файлу, тож токен одного кліпу не
приклеїш до кадрів іншого. Неправильний `captured_at` — невидима помилка: ламає
групування серій, добову активність і фенологію, і рік ніхто не помічає.

### Як вивчаються цифри
Без Tesseract і без знання шрифту. Калібрування питає одне: який час видно на
кадрі. Далі працює те, що годинник цокає — кадр *k* мусить показувати `t0 + k`
секунд, тож очікуваний символ у кожній позиції кожного кадру відомий, і
зіставлення цієї структури рівностей із кластерами однакових форм дає підпис
кожній цифрі. За 10 кадрів зазвичай з'являються всі десять.

### Дві розкладки, які підтримуються
- `LAYOUT_BAR` — смуга з суцільним фоном у кожному кадрі (Fujifilm-подібні AVI).
- `LAYOUT_CARD` — титульний кадр перед відео (Cuddeback). Титульний кадр **не**
  зберігається як фото (`ClipReading.card_index`), бо це чорна заставка.

Розкладка визначається сама, її не питають. Ведучі нулі й наявність секунд — теж.

### Що питають у формі
Модель камери (профіль зберігається в `camera_timestamp_profiles`), **порядок
дати**, ширина року, 12/24 год. Формат — не зручність: із незафіксованою шириною
року `2001/07/2014:02:33` так само читається як цілком правдоподібне
`2020-01-07 20:14:02`, і цей привид цокає по секунді на кадр так само, як
справжнє читання. Жодна перехресна перевірка його не викриє.

### Час з метаданих або вручну (з 2026-11-03, режим за замовчуванням)
- `video_metadata.py`: дата з `moov/mvhd` (MOV/MP4) або IDIT (AVI). Браузер шле лише
  заголовок, не відео. Значення = місцевий годинник камери, нічого не конвертується.
- SYPR MOV пише **початок** кліпу, NVTIM MOV **кінець**, UOVision і Fujifilm AVI дати
  не мають. Тому на сторінці перемикач «початок / кінець запису» і перший кадр поруч.
- Без дати час вписують вручну з першого кадру; час зміни файлу лише підказка
  (часто це час копіювання). `/api/video/sign-clip` відкидає рік < 2005 і майбутнє.
- За замовчуванням «Лише мініатюри».
- Харнес без БД: `scripts/video_upload_ui_harness.py` (порт 5080, `/__login`).

### Відомі межі
- **Третя родина камер не підтримується**: час намальовано просто поверх сцени,
  без підкладки (NVTIM MOV у `2 - Не сортовані/100NVTIM`). Пороги плоскості,
  яскравості й міжкадрової зміни її не відділяють — потрібен справжній детектор
  тексту. Поводиться безпечно: смуга не знаходиться, сторінка каже, що час не
  прочитано, вигаданої дати в базі не з'являється.
- **Cuddeback M4V браузер не ріже**: усередині MPEG-4 Part 2 (`mp4v`), який
  Chromium уже не декодує (звук грає, `videoWidth` лишається 0). Читач
  титульних карток готовий, але на справжніх файлах Cuddeback поки не працює.
- Метаданим контейнера вірити не можна: у Cuddeback `CreateDate` помилявся на
  дев'ять років. У NVTIM — правильний, але це не підстава довіряти взагалі.

### Деплой
1. Створити таблицю профілів (ідемпотентно):
   ```bash
   venv/bin/python -m scripts.init_video_upload
   ```
2. Коміти в сабмодулі окремо → оновити посилання в `biomon` і `myproject`.
3. Нових пакетів на проді не треба.

### ⚠️ Переклади модуля CT — власний домен
Цикл із розділу «Переклади (i18n)» вище стосується КОРЕНЕВОГО домену. У
`app/camera_traps` домен свій, і кореневий цикл для нього не робить нічого:
```bash
venv/Scripts/pybabel extract -F app/camera_traps/babel.cfg -k _l -k lazy_gettext -o app/camera_traps/messages.pot .
venv/Scripts/pybabel update -i app/camera_traps/messages.pot -d app/camera_traps/translations -D camera_traps
venv/Scripts/pybabel compile -f -d app/camera_traps/translations -D camera_traps
```
`extract` не приймає `-D` (падає), `update` і `compile` — приймають.
